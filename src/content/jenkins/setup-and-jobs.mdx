# Finishing Setup

After entering the initial admin password, the setup wizard walks you through:

1. **Install suggested plugins** — a sensible default set (Git, Pipeline, credentials).
2. **Create an admin user** — don't keep using the initial password.
3. **Set the Jenkins URL** — how Jenkins refers to itself in links and webhooks.

<Warning title="Secure it before exposing it">
Never expose a fresh Jenkins to the internet without authentication and HTTPS. An open Jenkins is a well-known target — attackers use it to run arbitrary builds (i.e. arbitrary code). Lock down security first.
</Warning>

# Jobs: Freestyle vs Pipeline

| Type | What it is | Best for |
|------|-----------|----------|
| **Freestyle** | Configured through the web UI with forms | Simple tasks, learning |
| **Pipeline** | Defined as code in a `Jenkinsfile` | Real projects (versioned, reviewable) |

<Tip title="Freestyle to learn, Pipeline for real">
Freestyle jobs are great for understanding the concepts. But production work belongs in a `Jenkinsfile` committed to your repo — it's version-controlled, code-reviewed, and reproducible. We'll build one next lesson.
</Tip>

# Creating a Freestyle Job

**New Item → Freestyle project.** The key sections:

- **Source Code Management** — point it at your Git repository URL and branch.
- **Build Triggers** — decide when it runs (poll SCM, webhook, schedule).
- **Build Steps** — the commands to execute.

A typical build step:

# Triggering Builds Automatically

You want builds to run when code changes, not only when you click. Two common approaches:

| Trigger | How it works |
|---------|--------------|
| **Webhook** | Git provider notifies Jenkins instantly on push (preferred) |
| **Poll SCM** | Jenkins checks the repo on a schedule (e.g. `H/5 * * * *`) |

<Tip title="Prefer webhooks">
Webhooks fire the moment a push happens — instant feedback and no wasted polling. Polling is a fallback for when your Git host can't reach Jenkins (e.g. behind a firewall).
</Tip>

The `H` in `H/5 * * * *` is Jenkins-specific: it spreads load by hashing the job name to pick a consistent-but-staggered minute, instead of every job firing at exactly the same time.

# 💼 Interview Preparation

<InterviewPrep question="What are important steps to secure a Jenkins instance?">
  Jenkins runs arbitrary code, so security is critical:

  - **Enable authentication and authorization** — never run it open; use role-based access control.
  - **Use HTTPS** and put it behind a reverse proxy or VPN, not directly on the public internet.
  - **Keep Jenkins and plugins updated** — plugins are a frequent source of vulnerabilities.
  - **Store credentials in the Credentials store**, never in job config or scripts.
  - **Run builds on agents, not the controller**, to limit what build code can touch.
  - **Restrict who can configure jobs**, since a job can execute anything.

  Treating Jenkins as a high-value target — because it is one — guides all of these decisions.
</InterviewPrep>
