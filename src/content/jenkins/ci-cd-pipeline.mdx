# The Pipeline Stages

A production CI/CD pipeline usually flows like this:

<CommandBlock command={`Checkout → Test → Build Image → Push Image → Deploy Staging → [Approve] → Deploy Prod`} language="text" />

Each stage builds on the last, and the approval gate ensures a human confirms before the highest-risk step.

---

# Building and Pushing a Docker Image

Using an image tagged with the build number gives every build a unique, traceable artifact:

<CommandBlock command={`stage('Build Image') {
  steps {
    sh 'docker build -t myapp:\${BUILD_NUMBER} .'
  }
}
stage('Push Image') {
  steps {
    withCredentials([usernamePassword(
      credentialsId: 'dockerhub',
      usernameVariable: 'USER',
      passwordVariable: 'PASS')]) {
      sh '''
        echo "\$PASS" | docker login -u "\$USER" --password-stdin
        docker push myapp:\${BUILD_NUMBER}
      '''
    }
  }
}`} language="groovy" />

<Tip title="Tag with the build number">
`myapp:${BUILD_NUMBER}` gives each build a unique tag, so you always know exactly which image is running and can roll back to a specific one. Avoid deploying `latest` to production — it's ambiguous.
</Tip>

---

# The Approval Gate

The `input` step pauses the pipeline and waits for a human to approve — perfect before a production deploy:

<CommandBlock command={`stage('Approve Production') {
  steps {
    input message: 'Deploy to production?', ok: 'Deploy'
  }
}
stage('Deploy Production') {
  steps {
    sh './deploy.sh production myapp:\${BUILD_NUMBER}'
  }
}`} language="groovy" />

<Terminal
  command="# Stage View, paused at the gate:"
  output={`Checkout        ✓
Test            ✓
Build Image     ✓
Push Image      ✓
Deploy Staging  ✓
Approve Prod    ⏸  Waiting: 'Deploy to production?'  [Deploy] [Abort]`}
/>

<Warning title="Guard the input step">
By default anyone with access can approve an `input`. Use the `submitter` parameter to restrict approval to specific users or groups, so only authorised people can release to production.
</Warning>

# Putting It All Together

The complete `Jenkinsfile`:

<CommandBlock command={`pipeline {
  agent any
  environment { IMAGE = "myapp:\${BUILD_NUMBER}" }

  stages {
    stage('Checkout') { steps { checkout scm } }
    stage('Test')     { steps { sh 'npm ci && npm test' } }
    stage('Build Image') { steps { sh 'docker build -t \$IMAGE .' } }
    stage('Push Image') {
      steps {
        withCredentials([usernamePassword(credentialsId: 'dockerhub',
          usernameVariable: 'USER', passwordVariable: 'PASS')]) {
          sh 'echo "\$PASS" | docker login -u "\$USER" --password-stdin && docker push \$IMAGE'
        }
      }
    }
    stage('Deploy Staging') { steps { sh './deploy.sh staging \$IMAGE' } }
    stage('Approve') { steps { input message: 'Deploy to production?', ok: 'Deploy' } }
    stage('Deploy Production') { steps { sh './deploy.sh production \$IMAGE' } }
  }

  post {
    failure { echo 'Build failed — notify the team' }
    always  { sh 'docker logout || true' }
  }
}`} language="groovy" />

# 💼 Interview Preparation

<InterviewPrep question="Describe a complete CI/CD pipeline you've designed or would design in Jenkins.">
  A strong answer walks the full lifecycle with safety built in:

  1. **Checkout** the code (multibranch, from a Jenkinsfile).
  2. **Test** — unit and integration tests; fail fast.
  3. **Build a Docker image** tagged with the build number for traceability.
  4. **Push** the image to a registry using credentials from the Credentials store.
  5. **Deploy to staging** automatically and run smoke tests.
  6. **Manual approval gate** (`input`) restricted to authorised submitters.
  7. **Deploy to production** using the exact same image that passed staging.
  8. **Post actions** — notify on failure, clean up always, keep artifacts for rollback.

  The principles that matter: test before you ship, promote the *same* artifact through environments, gate production, and make everything traceable and reversible.
</InterviewPrep>
