# Searching for Traces

The Zipkin UI lets you filter traces by service, span name, tags, duration, and time range. To hunt latency, sort by longest duration:

<CommandBlock command={`Search filters:
  serviceName = checkout
  minDuration = 500ms          # only slow requests
  tagQuery    = error=true     # or only failing ones
  lookback    = 1h`} language="text" />

This surfaces the exact slow or failing requests — not averages, but real individual journeys you can open and inspect.

<Tip title="Start from a symptom">
Don't browse traces at random. Start from a real complaint — "checkout p95 spiked at 2pm" — filter to that service, time, and a high `minDuration`, and open the worst offenders.
</Tip>

---

# Reading the Waterfall: The Critical Path

Open a trace and read the waterfall top-to-bottom. The **critical path** is the chain of spans that actually determines total duration.

<CommandBlock command={`GET /checkout                        820ms  ◀ total
├─ orders-service                    640ms
│  ├─ SELECT orders                   40ms
│  └─ payments-service               560ms  ◀ dominates
│     └─ POST bank-api  (x3 retries) 520ms  ◀ root cause
└─ inventory-service                  90ms  (parallel, not on critical path)`} language="text" />

Reading this: inventory ran in parallel and is cheap; the real cost is **payments → bank-api**, which is **retrying three times**. The fix isn't "optimize checkout" — it's "why is the bank API failing and retrying?"

---

# Common Problems Traces Reveal

| Pattern in the waterfall | Likely problem |
|--------------------------|----------------|
| Many tiny identical spans in a loop | **N+1 queries** — batch them |
| Same call repeated 3× back-to-back | **Retries** on a failing dependency |
| Long spans stacked sequentially | **Serial calls** that could run in parallel |
| A big gap between spans | Time lost in queue/GC/lock, not in a call |
| A span tagged `error=true` | A failure — open it for the exception detail |

<Warning title="A gap is a clue too">
Empty time *between* spans (where nothing is running) often means waiting — on a lock, a thread pool, a queue, or garbage collection. Don't just look at the bars; look at the gaps.
</Warning>

# The Dependency Diagram

Zipkin aggregates traces into a **service dependency graph** — who calls whom, and how often. It's invaluable for understanding an unfamiliar system:

<CommandBlock command={`gateway ──▶ orders ──▶ payments ──▶ bank-api
                │
                └────▶ inventory ──▶ warehouse-db`} language="text" />

Use it to spot surprises: a service calling one it shouldn't, an unexpectedly chatty edge, or a single dependency that everything funnels through (a availability risk).

---

# A Debugging Workflow

Put it together into a repeatable loop:

1. **Alert fires** (from your metrics) — latency or errors up on `checkout`.
2. **Search Zipkin** for slow/failing `checkout` traces in that window.
3. **Open the worst trace**, follow the critical path to the dominant span.
4. **Inspect that span's tags** and any error, or spot the retry/N+1 pattern.
5. **Check logs** for that exact `traceId` to get line-level detail.
6. **Fix and verify** — after deploying, new traces should show the span shrink.

<Tip title="Metrics + traces + logs together">
This is observability in practice: metrics *detected* it, the trace *localized* it, and logs (found by traceId) gave the *detail*. Each pillar hands off to the next.
</Tip>

# 🧪 Hands-on Lab

<Exercise title="Diagnose from the Trace">
  <div slot="tasks">
    A user reports slow product pages. This trace shows the problem — what is it, and what's your fix?

    ```
    GET /product/42               900ms
    ├─ product-service            880ms
    │  ├─ SELECT product           20ms
    │  ├─ SELECT review (id=1)     18ms
    │  ├─ SELECT review (id=2)     19ms
    │  ├─ SELECT review (id=3)     18ms
    │  └─ ... 40 more SELECT review spans
    ```
  </div>

  <div slot="solution">
    This is a classic **N+1 query** problem: one query for the product, then a separate query per review (40+ of them), each cheap but adding up to most of the 880ms. **Fix:** replace the per-review queries with a single batched query (e.g. `SELECT * FROM review WHERE product_id = 42`) or a join. The waterfall's repeated identical spans are the tell-tale sign.
  </div>
</Exercise>

# 💼 Interview Preparation

<InterviewPrep question="Walk me through using a trace to debug a latency spike.">
  A structured answer that ties observability together:

  1. **Detection** comes from metrics/alerts — e.g. checkout p95 latency spiked.
  2. **Search** Zipkin for slow traces of that service in the spike window, sorted by duration.
  3. **Open the worst trace** and follow the critical path to the span that dominates total time.
  4. **Diagnose the pattern**: is it one slow downstream call, retries against a failing dependency, an N+1 loop, or serial calls that could be parallel?
  5. **Drill down**: read the span's tags and error status; pull logs by the shared `traceId` for detail.
  6. **Fix and confirm**: after the change, new traces should show that span shrink and p95 recover.

  The key insight is that tracing turns "the system is slow" into "*this specific hop* is slow, for *this reason*."
</InterviewPrep>
