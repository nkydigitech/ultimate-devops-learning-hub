In a microservices system, a single user request might hop through an API gateway, three services, a cache, and a database. When it's slow, *which hop* is to blame? Metrics say "the system is slow"; logs are scattered across services. **Distributed tracing** stitches the whole journey together — and **Zipkin** is a classic, lightweight tool for doing it.

# The Microservices Debugging Problem

In a monolith, a slow request is one process — a profiler finds the bottleneck. In microservices, one request fans out across many services and machines:

<CommandBlock command={`Client ▶ Gateway ▶ Orders ▶ Payments ▶ Bank API
                     │
                     └─▶ Inventory ▶ Database

"Checkout is slow." ...but which of these hops caused it?`} language="text" />

Metrics tell you *that* latency is high. Logs from each service are hard to correlate. **Tracing** answers *where* the time went, by following one request end-to-end.

---

# Tracing vs. Metrics vs. Logs

| Pillar | Question it answers | Granularity |
|--------|---------------------|-------------|
| **Metrics** | How much / how fast, overall? | Aggregated numbers |
| **Logs** | What happened in detail, here? | Per-event, per-service |
| **Traces** | Where did *this request's* time go across services? | Per-request, cross-service |

They complement each other: metrics alert you, traces localize the problem, logs give the detail. This section focuses on **traces**.

<Tip title="Traces are per-request stories">
A metric is a number over time; a trace is the *story of a single request* as it travels through your system, timed at every step.
</Tip>

---

# What is Zipkin?

**Zipkin** is an open-source distributed tracing system (originally from Twitter). It **collects** timing data from your services and lets you **search and visualize** traces to find latency problems.

Its architecture has four parts:

<CommandBlock command={`Instrumented services ──spans──▶ Collector ──▶ Storage ──▶ UI / API
   (send timing data)                          (in-memory,   (search &
                                                Cassandra,    visualize
                                                Elasticsearch) traces)`} language="text" />

| Component | Role |
|-----------|------|
| **Reporter** (in your app) | Records timing and sends it to Zipkin |
| **Collector** | Receives and validates incoming span data |
| **Storage** | Stores traces (in-memory for demos; Elasticsearch/Cassandra for real use) |
| **UI / API** | Search traces and view the waterfall timeline |

---

# A Trace, Visually

Zipkin shows a trace as a **waterfall** — each service's work is a bar, positioned by when it happened and sized by how long it took:

<CommandBlock command={`Trace: GET /checkout   (total 820ms)
gateway  ├────────────────────────────────────┤ 820ms
orders     ├──────────────────────────────┤     640ms
payments        ├────────────────────┤           480ms  ◀ the bottleneck
inventory  ├───┤                                  90ms`} language="text" />

At a glance you can see **payments** dominated the request. That's the power of tracing: the slow hop is obvious.

# 💼 Interview Preparation

<InterviewPrep question="When would tracing help you where metrics and logs fall short?">
  Tracing shines for cross-service latency and causality problems:

  - **Metrics** tell you the checkout endpoint's p95 latency jumped — but not *why* or *where*.
  - **Logs** exist per service, but correlating them across five services for one request is painful without a shared ID.
  - **Traces** tie the whole request together with a trace ID and show a timed waterfall, so the slow service (or the surprising extra call, or the retry storm) is immediately visible.

  So: metrics to detect and alert, traces to localize the culprit across services, logs to get the fine detail once you know where to look.
</InterviewPrep>
