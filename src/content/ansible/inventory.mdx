Before Ansible can configure servers, it needs to know they exist. That's the **inventory**. Once it does, **ad-hoc commands** let you run a single action across every server instantly — perfect for quick checks before you write full playbooks.

---

By the end of this lesson you will:

- Write an inventory file and organize hosts into groups
- Test connectivity with the `ping` module
- Run ad-hoc commands across servers
- Understand when to use ad-hoc vs a playbook

# The Inventory File

An inventory lists your managed nodes, optionally grouped. Here's a simple `inventory.ini`:

<CommandBlock command={`[web]
web-01 ansible_host=203.0.113.10
web-02 ansible_host=203.0.113.11

[db]
db-01 ansible_host=203.0.113.20

[all:vars]
ansible_user=ubuntu`} language="ini" />

- `[web]` and `[db]` are **groups** — you can target a whole group at once.
- `[all:vars]` sets variables (like the SSH user) for every host.

<Tip title="Groups are how you target servers">
Grouping lets you say "run this on all web servers" or "only the database". Real inventories group by role (web/db/cache), environment (prod/staging), or region.
</Tip>

---

# Test Connectivity: the ping Module

The first thing to run against any new inventory — it confirms Ansible can reach and authenticate to each host:

<CommandBlock command={`ansible all -i inventory.ini -m ping`} />

<Terminal
  command="ansible web -i inventory.ini -m ping"
  output={`web-01 | SUCCESS => {
    "changed": false,
    "ping": "pong"
}
web-02 | SUCCESS => {
    "changed": false,
    "ping": "pong"
}`}
/>

<Warning title="Ansible ping is not ICMP">
The `ping` module doesn't send network pings — it connects over SSH and checks Python is usable on the target. A `SUCCESS ... "pong"` means the whole connection + auth path works.
</Warning>

# Ad-Hoc Commands

An ad-hoc command runs a **single module** against hosts without writing a playbook. The shape is:

<CommandBlock command={`ansible <group> -i inventory.ini -m <module> -a "<arguments>"`} language="text" />

Some useful examples:

<CommandBlock command={`# Check uptime on all web servers
ansible web -i inventory.ini -m command -a "uptime"

# Check disk space everywhere
ansible all -i inventory.ini -m command -a "df -h /"

# Install nginx (needs sudo -> --become)
ansible web -i inventory.ini -m apt -a "name=nginx state=present" --become`} />

<Tip title="--become = sudo">
`--become` tells Ansible to escalate privileges (run as root via sudo) for tasks that need it, like installing packages or editing system files.
</Tip>

---

# Ad-Hoc vs Playbook

| Use ad-hoc when... | Use a playbook when... |
|--------------------|------------------------|
| One quick action (restart, check) | Multiple steps that belong together |
| Exploring / troubleshooting | You want it repeatable and version-controlled |
| No need to keep it | It's part of your standard setup |

Ad-hoc is the "quick command" mode; playbooks (next lesson) are the durable, reusable mode.

# 💼 Interview Preparation

<InterviewPrep question="How do you organize an Ansible inventory for a real environment?">
  A practical answer covers structure and separation:

  - **Group by role:** `[web]`, `[db]`, `[cache]` so you can target servers by what they do.
  - **Separate environments:** keep `production` and `staging` inventories apart (separate files or directories) so a command can never accidentally hit prod when you meant staging.
  - **Use group variables:** put shared settings (SSH user, ports, package versions) in `group_vars/` rather than repeating them per host.
  - **Consider dynamic inventory:** in the cloud, servers come and go — a dynamic inventory plugin (for AWS, Azure, etc.) generates the host list automatically from the provider's API instead of a static file.

  The goal is an inventory that's clearly grouped, keeps environments isolated, and stays accurate as infrastructure changes.
</InterviewPrep>
