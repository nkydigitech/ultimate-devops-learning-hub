A **playbook** is a YAML file that describes the desired state of your servers as an ordered list of tasks. Unlike ad-hoc commands, playbooks are reusable, readable, and version-controlled — this is how Ansible is used in real projects.

# Anatomy of a Playbook

Here's a complete playbook that installs and starts nginx on all web servers — `webserver.yml`:

<CommandBlock command={`---
- name: Configure web servers
  hosts: web
  become: true

  tasks:
    - name: Install nginx
      apt:
        name: nginx
        state: present
        update_cache: true

    - name: Ensure nginx is running and enabled
      service:
        name: nginx
        state: started
        enabled: true`} language="yaml" />

Reading it top to bottom:

- **`hosts: web`** — target the `web` group from the inventory.
- **`become: true`** — run with sudo.
- **`tasks:`** — an ordered list; each task calls a **module** (`apt`, `service`) with parameters.
- **`name:`** — a human-readable label shown in the output.

<Warning title="YAML is whitespace-sensitive">
Like Python, YAML uses indentation for structure — always spaces, never tabs. A single misaligned line will cause a parse error. Keep indentation consistent (2 spaces per level is the convention).
</Warning>

# Run the Playbook

<CommandBlock command={`ansible-playbook -i inventory.ini webserver.yml`} />

<Terminal
  command="ansible-playbook -i inventory.ini webserver.yml"
  output={`PLAY [Configure web servers] **************************

TASK [Install nginx] **********************************
changed: [web-01]
changed: [web-02]

TASK [Ensure nginx is running and enabled] ************
ok: [web-01]
ok: [web-02]

PLAY RECAP ********************************************
web-01  : ok=3  changed=1  unreachable=0  failed=0
web-02  : ok=3  changed=1  unreachable=0  failed=0`}
/>

Run it **again** and watch `changed` drop to `0` — everything is already in the desired state. That's **idempotency** in action.

# Variables and Handlers

**Variables** keep playbooks flexible:

<CommandBlock command={`- name: Configure web servers
  hosts: web
  become: true
  vars:
    package_name: nginx

  tasks:
    - name: Install the web server
      apt:
        name: "{{ package_name }}"
        state: present`} language="yaml" />

**Handlers** run only when notified by a changed task — ideal for restarting a service *only* when its config actually changed:

<CommandBlock command={`  tasks:
    - name: Copy nginx config
      copy:
        src: nginx.conf
        dest: /etc/nginx/nginx.conf
      notify: Restart nginx

  handlers:
    - name: Restart nginx
      service:
        name: nginx
        state: restarted`} language="yaml" />

<Tip title="Why handlers matter">
Without a handler you'd restart nginx on every run. With one, nginx restarts **only** when the config file actually changed — no needless service disruptions. That's the idempotent mindset applied to side effects.
</Tip>

# 💼 Interview Preparation

<InterviewPrep question="What makes a good, maintainable Ansible playbook?">
  Several qualities interviewers value:

  - **Idempotent by design:** use modules (`apt`, `service`, `copy`) that describe desired state rather than `command`/`shell` running raw commands — so re-runs are safe.
  - **Descriptive `name:` on every task:** the output becomes self-documenting and easy to debug.
  - **Variables over hardcoding:** put values in `vars`, `group_vars`, or `host_vars` so one playbook works across environments.
  - **Handlers for restarts:** restart services only when something actually changed.
  - **Roles for structure:** as playbooks grow, split reusable pieces into **roles** (a standard directory layout for tasks, handlers, templates, and variables) so they can be shared and reused.
  - **Version-controlled and tested:** keep playbooks in Git and validate with `--check` (dry run) before applying to production.

  In short: declarative, readable, parameterised, and safe to re-run.
</InterviewPrep>
