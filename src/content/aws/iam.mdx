**IAM (Identity and Access Management)** is how AWS decides *who* is allowed to do *what*. Get IAM right and your account is secure; get it wrong and you've handed the keys to attackers. It's free, and it's the first thing to master in any cloud.

# The Four IAM Building Blocks

| Concept | What it is |
|---------|-----------|
| **User** | A person or app with long-term credentials |
| **Group** | A collection of users sharing permissions (e.g. `Developers`) |
| **Policy** | A JSON document that grants or denies specific actions |
| **Role** | A set of permissions that can be *assumed* temporarily — by a user, service, or EC2 instance |

---

# Policies: the Rules Themselves

A policy is JSON that says which **actions** are allowed on which **resources**:

<CommandBlock command={`{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:ListBucket"],
    "Resource": "arn:aws:s3:::my-app-bucket/*"
  }]
}`} language="json" />

This policy allows **reading** objects from one specific bucket — and nothing else.

<Tip title="Principle of Least Privilege">
Grant only the permissions actually needed to do the job — no more. Start with nothing and add access as required, rather than granting broad access and hoping to lock it down later.
</Tip>

---

# Roles Beat Long-Lived Keys

A common mistake is storing an access key on a server. Instead, attach an **IAM role** to the EC2 instance — AWS then hands it short-lived, auto-rotating credentials.

<Warning title="Never do this">
Never hard-code AWS access keys in your code, commit them to Git, or bake them into an EC2 instance. Leaked keys are one of the most common causes of cloud breaches. Use **roles** for services and **short-lived credentials** for humans.
</Warning>

# 🧪 Hands-on Lab

<Exercise title="Create a Least-Privilege User">
  <div slot="tasks">
    In the AWS Console:

    1. Enable **MFA** on your root account (then stop using root for daily work).
    2. Create an IAM **group** called `Developers`.
    3. Attach a policy that grants only what's needed (e.g. read-only S3).
    4. Create a **user**, add them to the group, and test with the CLI.
  </div>

  <div slot="solution">
    <Terminal
      command="aws iam list-groups-for-user --user-name ada"
      output={`{
  "Groups": [
    { "GroupName": "Developers", "Arn": "arn:aws:iam::123456789012:group/Developers" }
  ]
}`}
    />
  </div>
</Exercise>

# 💼 Interview Preparation

<InterviewPrep question="Why are IAM roles preferred over IAM user access keys for applications?">
  IAM **roles** provide **temporary, automatically-rotated credentials** that AWS delivers to a service (like EC2, Lambda, or ECS) on demand. There's no long-lived secret to store, leak, or manually rotate.

  IAM **user access keys** are long-lived static secrets. If one is committed to Git or left on a server, it can be stolen and used indefinitely until someone notices and revokes it.

  So for any application or AWS service that needs access, best practice is to assign a role scoped with least privilege — the app never sees a permanent key at all.
</InterviewPrep>
