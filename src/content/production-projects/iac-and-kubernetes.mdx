# Step 1 — Provision Infrastructure with Terraform

Rather than clicking around a cloud console, you declare the cluster in code. A minimal example provisioning a managed cluster:

<CommandBlock command={`# main.tf
terraform {
  backend "s3" {                 # remote state (see below)
    bucket = "my-tf-state"
    key    = "prod/cluster.tfstate"
    region = "us-east-1"
  }
}

module "cluster" {
  source          = "terraform-aws-modules/eks/aws"
  cluster_name    = "portfolio-cluster"
  cluster_version = "1.30"
  # ... vpc, node groups, etc.
}

output "cluster_endpoint" {
  value = module.cluster.cluster_endpoint
}`} language="hcl" />

The workflow is always the same three commands:

<CommandBlock command={`terraform init      # download providers, connect backend
terraform plan      # preview what will change (review this!)
terraform apply     # create the infrastructure`} language="bash" />

<Warning title="Always read the plan">
`terraform plan` shows exactly what will be created, changed, or destroyed. Never `apply` in production without reading it — a careless change can destroy and recreate a database. The plan is your safety review.
</Warning>

---

# Step 2 — Use Remote State

Notice the `backend "s3"` block. Terraform tracks reality in a **state file**. Keeping it on your laptop is a disaster waiting to happen — lost laptop, no teamwork, conflicting changes. **Remote state** (S3, GCS, Terraform Cloud) fixes this:

- **Shared** — the whole team works from one source of truth
- **Locked** — prevents two people applying at once and corrupting state
- **Durable & versioned** — survives your machine and can be rolled back

<Tip title="State is sensitive">
The state file can contain secrets (passwords, keys) in plaintext. Store it in an encrypted, access-controlled backend — never commit it to Git.
</Tip>

# Step 3 — Deploy to Kubernetes

With the cluster up, deploy your Project 1 image. A production-worthy Deployment includes **probes** and **resource limits** — not just the bare minimum:

<CommandBlock command={`apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3
  selector:
    matchLabels: { app: myapp }
  template:
    metadata:
      labels: { app: myapp }
    spec:
      containers:
        - name: myapp
          image: ghcr.io/you/myapp:a1b2c3d      # deploy by SHA, not latest
          ports:
            - containerPort: 3000
          livenessProbe:                          # restart if hung
            httpGet: { path: /health, port: 3000 }
            initialDelaySeconds: 5
          readinessProbe:                         # don't send traffic until ready
            httpGet: { path: /health, port: 3000 }
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits:   { cpu: "500m", memory: "256Mi" }`} language="yaml" />

Expose it with a Service so traffic can reach the pods:

<CommandBlock command={`apiVersion: v1
kind: Service
metadata:
  name: myapp
spec:
  type: LoadBalancer
  selector: { app: myapp }
  ports:
    - port: 80
      targetPort: 3000`} language="yaml" />

<Terminal
  command="kubectl apply -f k8s/ && kubectl get pods"
  output={`deployment.apps/myapp created
service/myapp created

NAME                     READY   STATUS    RESTARTS   AGE
myapp-7d9f8c6b4-2xk9p    1/1     Running   0          20s
myapp-7d9f8c6b4-8mn4q    1/1     Running   0          20s
myapp-7d9f8c6b4-p7wz3    1/1     Running   0          20s`}
/>

# Step 4 — Autoscale

Let Kubernetes add and remove pods based on load with a HorizontalPodAutoscaler:

<CommandBlock command={`apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }`} language="yaml" />

Now the app scales out past 3 pods when CPU crosses 70%, and back in when load drops — capacity that follows demand, defined declaratively.

# 🧪 Hands-on Lab

<Exercise title="Explain the Probes">
  <div slot="tasks">
    Your app occasionally hangs (still "running" but not responding), and during startup it briefly returns errors before it's ready. Which probe addresses each problem, and what would happen without them?
  </div>

  <div slot="solution">
    - **Liveness probe** handles the *hang*: when `/health` stops responding, Kubernetes restarts the pod. Without it, a hung pod would keep receiving traffic and failing forever.
    - **Readiness probe** handles *startup*: the pod is kept out of the Service's load balancer until `/health` succeeds. Without it, users would hit the pod during its error-y startup window.

    Together they give you self-healing and zero-downtime rollouts — core reasons Kubernetes is production-grade.
  </div>
</Exercise>

# 💼 Interview Preparation

<InterviewPrep question="Walk through how you'd deploy a containerised app to production on Kubernetes.">
  A complete answer moves from infrastructure to a resilient deployment:

  1. **Provision with Terraform** — declare the cluster and networking as code, use **remote, locked state**, and always review `terraform plan` before `apply`.
  2. **Deploy by immutable image tag** (the commit SHA from CI), never `latest`, so the running version is known.
  3. **Add resilience**: liveness and readiness probes (self-healing + zero-downtime rollouts), and **resource requests/limits** so the scheduler can place pods and one app can't starve others.
  4. **Expose** via a Service (and Ingress for HTTP routing/TLS).
  5. **Autoscale** with an HPA based on CPU or custom metrics.

  I'd also mention rolling updates for safe deploys and keeping everything — Terraform and manifests — in Git, which sets up the GitOps workflow next.
</InterviewPrep>
