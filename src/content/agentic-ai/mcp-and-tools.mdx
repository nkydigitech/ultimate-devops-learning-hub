An LLM on its own can only produce text. To *act* — read a file, query an API, restart a service — it needs **tools**. The **Model Context Protocol (MCP)** is an open standard for connecting models to those tools and data sources in a consistent way. Together they turn a chatbot into a capable agent.

# What Is a Tool?

A **tool** is a function the model is allowed to call. You describe it — its name, what it does, and its inputs — and the model can choose to invoke it during its reasoning.

<CommandBlock command={`{
  "name": "get_pod_logs",
  "description": "Fetch recent logs for a Kubernetes pod",
  "parameters": {
    "pod_name": "string",
    "lines": "number"
  }
}`} language="json" />

Given this description, the model can decide *when* to call `get_pod_logs`, with what arguments — and then reason over the result.

---

# The Tool-Calling Flow

<CommandBlock command={`1. Model decides: "I need the logs for web-abc"
2. Model emits:   get_pod_logs(pod_name="web-abc", lines=50)
3. Your code runs the real function
4. Result returned to the model
5. Model reasons over the logs and responds`} language="text" />

The crucial point: the **model doesn't run anything itself**. It *requests* a tool call; your code executes it and returns the result. That boundary is where you enforce security and permissions.

<Warning title="The model requests, you control">
Never let a model directly execute commands. It should only *ask* to call a defined tool; your code validates the request, applies permissions, runs it, and returns the result. This boundary is your primary safety control.
</Warning>

# The Problem MCP Solves

Before MCP, every AI app connected to every tool in its own custom way. Ten apps × ten tools meant a hundred bespoke integrations — brittle and duplicated.

**MCP** standardises this. Build an MCP **server** for a system once (say, a GitHub server or a Kubernetes server), and *any* MCP-compatible AI app can use it. It's often described as *"USB-C for AI"* — one standard connector.

<CommandBlock command={`Without MCP:  every app ↔ every tool  (N × M custom integrations)

With MCP:     apps ─┐                 ┌─ tools
                    ├─ MCP standard ──┤
                    ┘                 └─`} language="text" />

---

# MCP Client and Server

MCP follows a simple client/server model:

| Role | What it is |
|------|------------|
| **MCP Server** | Exposes tools, data, and prompts for one system (files, GitHub, a database) |
| **MCP Client** | The AI application that connects to servers and uses their tools |

An MCP server can offer three things:

- **Tools** — actions the model can call (e.g. `create_issue`).
- **Resources** — data the model can read (e.g. a file's contents).
- **Prompts** — reusable prompt templates for common tasks.

<Tip title="Why this matters for DevOps">
MCP means you can wire an agent to your real toolchain — Git, cloud APIs, monitoring, ticketing — through standard servers, instead of gluing together one-off integrations. That's what makes practical, tool-using DevOps agents feasible.
</Tip>

# 💼 Interview Preparation

<InterviewPrep question="Explain how an AI agent safely interacts with real systems through tools and MCP.">
  Several layers work together:

  - **Tools** are explicitly defined functions with names, descriptions, and typed parameters — the only actions the model may request.
  - **The request/execute boundary** means the model *asks* to call a tool; your code validates the request, applies permissions, executes it, and returns the result. The model never runs anything directly.
  - **MCP** standardises this so tools and data sources (Git, cloud, monitoring) are exposed by reusable servers that any compatible agent can use.
  - **Guardrails** — read-only tools run freely; destructive tools require human approval; every call is logged and audited.

  This design gives an agent real capability while keeping a human firmly in control of anything risky.
</InterviewPrep>
