# Triggers — the `on` Key

The `on` key decides what events start the workflow:

<CommandBlock command={`on:
  push:
    branches: [main]           # only pushes to main
  pull_request:
    branches: [main]           # PRs targeting main
  schedule:
    - cron: "0 6 * * *"        # every day at 06:00 UTC
  workflow_dispatch:           # a manual "Run" button`} language="yaml" />

| Trigger | Fires when |
|---------|------------|
| `push` | Commits are pushed |
| `pull_request` | A PR is opened/updated |
| `schedule` | On a cron schedule |
| `workflow_dispatch` | You click "Run workflow" manually |

<Tip title="Filter to what matters">
Restrict triggers with `branches`, `paths`, or `tags` so workflows only run when relevant — this saves runner minutes and avoids noise.
</Tip>

# Jobs and Steps

A workflow has one or more **jobs**; each job has ordered **steps**:

<CommandBlock command={`jobs:
  test:
    runs-on: ubuntu-latest       # the runner OS
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci               # install
      - run: npm test             # test`} language="yaml" />

By default, **jobs run in parallel**. Steps within a job run **in order**, sharing the same runner and filesystem.

---

# Job Dependencies

Use `needs` to make one job wait for another — essential for build → deploy ordering:

<CommandBlock command={`jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "building"

  deploy:
    needs: build            # only runs if build succeeds
    runs-on: ubuntu-latest
    steps:
      - run: echo "deploying"`} language="yaml" />

<Warning title="Jobs don't share files automatically">
Each job runs on a fresh runner. To pass files (like build output) from one job to another, upload them as an **artifact** in the first job and download them in the next. Steps within the same job *do* share files.
</Warning>

---

# Matrix Builds

A **matrix** runs the same job across multiple configurations in parallel — perfect for testing several language versions:

<CommandBlock command={`jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        node: [18, 20, 22]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: \${{ matrix.node }}
      - run: npm test`} language="yaml" />

This automatically creates three parallel jobs — one each for Node 18, 20, and 22.

---

# Caching for Speed

Reinstalling dependencies every run is slow. Cache them to speed things up dramatically:

<CommandBlock command={`- uses: actions/setup-node@v4
  with:
    node-version: 20
    cache: 'npm'          # cache the npm dependency store`} language="yaml" />

<Tip title="Expressions and context">
The double-brace expression syntax is how workflows read context values — the commit SHA, a matrix value, or a secret — and inject them into steps. You'll see it used constantly in the pipelines ahead.
</Tip>

# 💼 Interview Preparation

<InterviewPrep question="How do you pass build artifacts between jobs in GitHub Actions?">
  Because each job runs on a fresh runner, files don't carry over automatically. The standard approach:

  1. In the **build job**, produce your output and upload it with `actions/upload-artifact`.
  2. In the **downstream job**, add `needs: build` so it runs after, and download the files with `actions/download-artifact`.

  For dependencies (not build output), use **caching** (`actions/cache` or the `cache:` option on setup actions) to reuse them across runs. Knowing the difference — artifacts for passing files between jobs, cache for reusing dependencies across runs — is a common interview distinction.
</InterviewPrep>
