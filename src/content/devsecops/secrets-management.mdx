# The Danger of Hard-Coded Secrets

Putting a secret in code feels convenient. It's a disaster:

<Warning title="Git never forgets">
Committing a secret and then deleting it does NOT remove it — it stays in the Git history forever, readable by anyone with repo access. Once a secret hits a remote repo, treat it as **compromised** and rotate it immediately. Automated bots scan public GitHub for leaked keys within seconds.
</Warning>

<CommandBlock command={`# NEVER do this
const dbPassword = "SuperSecret123";
const apiKey = "sk_live_abc123...";

# Do this — read from the environment / a secret store
const dbPassword = process.env.DB_PASSWORD;`} language="javascript" />

# Catch Secrets Before They're Committed

Prevention beats cleanup. Two layers:

**1. Pre-commit hooks** stop a secret from ever being committed:

<CommandBlock command={`# Using gitleaks as a pre-commit hook
gitleaks protect --staged --verbose`} language="bash" />

**2. CI scanning** catches anything that slips through:

<Terminal
  command="gitleaks detect --source . --verbose"
  output={`Finding:     AWS Access Key
Secret:      AKIA************
File:        config/settings.py
Line:        14
Commit:      3a9f1c2

leaks found: 1`}
/>

<Tip title="Defence in depth">
Run secret scanning both locally (pre-commit) and in CI. The pre-commit hook is your first line; the CI scan is the safety net for developers who bypass or lack the hook.
</Tip>

# Secrets Managers / Vaults

Instead of scattering secrets in env files, store them in a dedicated **secrets manager** that provides encryption, access control, and auditing:

| Tool | Where it lives |
|------|----------------|
| **HashiCorp Vault** | Self-hosted, cloud-agnostic |
| **AWS Secrets Manager** | AWS |
| **Azure Key Vault** | Azure |
| **GCP Secret Manager** | Google Cloud |

Apps fetch secrets at runtime, authenticated by their identity:

<CommandBlock command={`# App requests a secret at startup, using its own identity
vault kv get -field=password secret/prod/db

# It's never stored on disk — fetched into memory when needed`} language="bash" />

Benefits over env files: **central control**, **encryption at rest**, **audit logs** of who accessed what, and easy **rotation**.

---

# Rotation and Least Privilege

Two principles limit the damage if a secret *does* leak:

- **Rotation** — change secrets regularly and automatically. A leaked secret that's already been rotated is worthless. Short-lived, dynamically generated credentials are the gold standard.
- **Least privilege** — each secret grants the minimum access needed. A read-only database credential can't be used to delete data even if stolen.

<Tip title="Scope every credential tightly">
Never use one all-powerful admin key everywhere. Give each service its own narrowly scoped credential. If one leaks, the blast radius is small and contained.
</Tip>

# 💼 Interview Preparation

<InterviewPrep question="How do you manage secrets securely across the development lifecycle?">
  A layered strategy from commit to runtime:

  - **Never hard-code** secrets; read them from the environment or a secrets manager.
  - **Prevent leaks** with pre-commit secret scanning and CI scanning as a safety net.
  - **Store centrally** in a vault (HashiCorp Vault, AWS/Azure/GCP secret managers) with encryption and access control.
  - **Inject at runtime** authenticated by the service's own identity — secrets never sit on disk or in images.
  - **Rotate regularly**, ideally with short-lived, dynamically generated credentials.
  - **Least privilege** — scope each credential to the minimum access it needs.
  - **Audit** every secret access, and if one leaks, rotate immediately.

  The mindset: assume any secret *could* leak, and design so that a leak is caught early and does minimal damage.
</InterviewPrep>
