Containers are how modern software ships, so securing them is essential. Container security spans the whole lifecycle: the **image** you build, the **scan** before you ship, and the **runtime** settings that constrain a container in production. This lesson ties DevSecOps back to the Docker and Kubernetes skills you already have.

# Start with a Minimal Image

The smaller the image, the smaller the attack surface. Every extra package is a potential vulnerability.

| Choice | Attack surface |
|--------|----------------|
| Full OS image (e.g. `ubuntu`) | Large — many packages, shells, tools |
| Slim image (e.g. `-slim`) | Smaller |
| Alpine (e.g. `node:20-alpine`) | Small |
| Distroless / scratch | Minimal — no shell, no package manager |

<Tip title="No shell, no shell exploits">
Distroless images contain only your app and its runtime — no shell, no package manager. An attacker who breaks in finds almost nothing to work with. It's one of the highest-value hardening steps.
</Tip>

---

# Never Run as Root

By default containers run as root. If an attacker escapes the app, root inside the container is a dangerous starting point. Drop to a non-root user:

<CommandBlock command={`FROM node:20-slim

# Create and switch to a non-root user
RUN useradd --system --uid 1001 appuser
WORKDIR /app
COPY --chown=appuser:appuser . .
RUN npm ci --production

USER appuser              # everything below runs as appuser
EXPOSE 3000
CMD ["node", "server.js"]`} language="dockerfile" />

<Warning title="Root in a container is root-adjacent on the host">
A container running as root that suffers a breakout has a far easier path to compromising the host. Running as an unprivileged user is one of the single most effective container hardening measures.
</Warning>

---

# Scan Images in CI

Base images and dependencies accumulate known vulnerabilities over time. Scan every image before it ships:

<CommandBlock command={`# Fail the build on high/critical image vulnerabilities
trivy image --exit-code 1 --severity HIGH,CRITICAL myapp:1.0`} language="bash" />

<Terminal
  command="trivy image --severity HIGH,CRITICAL myapp:1.0"
  output={`myapp:1.0 (debian 12)
Total: 3 (HIGH: 2, CRITICAL: 1)

The base image is outdated. Rebuild on a patched base
(node:20-slim latest) to clear these findings.`}
/>

<Tip title="Rebuild regularly">
Even if your code doesn't change, rebuild images periodically to pick up patched base layers. An image built six months ago likely carries vulnerabilities fixed since.
</Tip>

# Harden the Runtime in Kubernetes

Securing the image isn't enough — constrain the container at runtime too, using a **securityContext**:

<CommandBlock command={`spec:
  containers:
    - name: app
      image: myapp:1.0
      securityContext:
        runAsNonRoot: true          # refuse to run as root
        runAsUser: 1001
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true # filesystem is immutable
        capabilities:
          drop: ["ALL"]             # drop all Linux capabilities`} language="yaml" />

Each setting shrinks what a compromised container can do:

- `runAsNonRoot` / `runAsUser` — no root.
- `allowPrivilegeEscalation: false` — can't gain more privileges.
- `readOnlyRootFilesystem` — attacker can't write malware to disk.
- `drop: ["ALL"]` — remove Linux capabilities the app doesn't need.

<Tip title="Enforce cluster-wide">
Use Pod Security Standards or a policy engine (like Kyverno or OPA Gatekeeper) to *enforce* these settings across the whole cluster, so no one can deploy an unhardened container by accident.
</Tip>

# 💼 Interview Preparation

<InterviewPrep question="How do you secure containers across their lifecycle?">
  Defence in depth, from build to runtime:

  - **Minimal base images** — slim, alpine, or distroless to shrink the attack surface.
  - **Non-root user** — never run the app as root inside the container.
  - **Image scanning in CI** — fail builds on high/critical vulnerabilities; rebuild regularly for patched bases.
  - **No secrets in images** — inject them at runtime from a secrets manager.
  - **Runtime hardening** — Kubernetes `securityContext`: non-root, no privilege escalation, read-only filesystem, drop all capabilities.
  - **Policy enforcement** — Pod Security Standards or Kyverno/OPA to enforce these cluster-wide.
  - **Runtime monitoring** — detect anomalous container behaviour in production.

  The principle mirrors all of DevSecOps: minimise attack surface, apply least privilege, automate the checks, and assume breach — so each layer limits the damage of the one before failing.
</InterviewPrep>
