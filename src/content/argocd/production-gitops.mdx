# The App of Apps Pattern

Instead of creating each Application by hand, you create **one parent Application** that itself points at a folder of *child* Application manifests. Argo CD then manages the children automatically.

<CommandBlock command={`root-app (Application)
  └─ points at git path "apps/"
       ├─ app-frontend.yaml   (Application)
       ├─ app-backend.yaml    (Application)
       ├─ app-monitoring.yaml (Application)
       └─ app-argocd.yaml     (Application)  ← even Argo CD config itself`} language="text" />

Now onboarding a new service is a single commit — add its Application YAML to `apps/` and the root app syncs it into existence. This is how teams manage fleets of apps from one Git repo.

# Structuring Your Repos

A common, clean layout separates *what the app is* from *how each environment configures it*, using **Kustomize** overlays:

<CommandBlock command={`my-app/
├── base/                 # shared manifests
│   ├── deployment.yaml
│   ├── service.yaml
│   └── kustomization.yaml
└── overlays/
    ├── dev/
    │   └── kustomization.yaml   # e.g. 1 replica, debug on
    ├── staging/
    │   └── kustomization.yaml
    └── prod/
        └── kustomization.yaml   # e.g. 5 replicas, resource limits`} language="text" />

Each environment gets its own Argo CD Application pointing at the matching overlay path. The base stays DRY; overlays hold only the differences.

<Tip title="Config repo vs. app repo">
A widely used practice is to keep application *source code* in one repo and the *deployment manifests* in a separate "config" repo. CI builds the image and bumps the image tag in the config repo; Argo CD sees the commit and deploys. This cleanly separates "build" from "deploy".
</Tip>

# Production Best Practices

- **Everything in Git** — no manual `kubectl apply` in production. If it's not in Git, it doesn't exist.
- **Enable `selfHeal` and `prune`** in production so drift can't accumulate.
- **Protect branches** — require pull-request review for the config repo; that review *is* your deployment approval.
- **Promote by PR** — moving from staging to prod is a pull request bumping a version, giving you a full audit trail.
- **Use Projects (AppProjects)** to restrict which repos, clusters, and namespaces a set of apps may touch — essential for multi-team clusters.
- **Sync notifications** — wire Argo CD notifications to Slack so the team sees deploys and failures.

<Warning title="Secrets don't belong in plain Git">
Never commit raw secrets. Use Sealed Secrets, External Secrets Operator, or a vault integration so the Git repo holds only encrypted or referenced secrets, not plaintext credentials.
</Warning>

# Rollback the GitOps Way

Because Git is the source of truth, rollback is just Git:

<CommandBlock command={`# revert the bad change — Argo CD re-syncs to the previous state
git revert <bad-commit>
git push

# or roll an app back to a previous revision directly
argocd app rollback my-app <history-id>`} />

No special tooling, no snowflake procedure — the same workflow you already use for code.

# 💼 Interview Preparation

<InterviewPrep question="How would you manage 30 microservices across three environments with Argo CD?">
  A scalable answer combines a few patterns:

  - **App of Apps** (or ApplicationSets) so all services are declared in one place and onboarding is a single commit.
  - **Kustomize/Helm overlays** with a shared base and per-environment overlays for the differences.
  - **A separate config repo** with branch protection, so every deploy is a reviewed PR — that review is the approval.
  - **AppProjects** to scope which repos/clusters/namespaces each team can deploy to.
  - **selfHeal + prune** in prod, secrets handled via a sealed-secrets or external-secrets mechanism, and Slack notifications for visibility.

  The result: dozens of services deploy safely, auditable through Git, with drift automatically corrected.
</InterviewPrep>
