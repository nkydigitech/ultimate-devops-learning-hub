# Manual vs. Automated Sync

By default, sync is manual — Argo CD shows `OutOfSync` and waits for you. Turn on **automated sync** and it applies changes as soon as Git changes:

<CommandBlock command={`spec:
  syncPolicy:
    automated:
      prune: true        # delete resources removed from Git
      selfHeal: true     # revert manual changes made in the cluster
    syncOptions:
      - CreateNamespace=true`} language="yaml" />

Two flags do the heavy lifting:

| Option | What it does |
|--------|--------------|
| **`prune`** | When you delete a manifest from Git, Argo CD deletes it from the cluster too |
| **`selfHeal`** | When someone changes the live cluster by hand, Argo CD reverts it back to Git |

<Warning title="Prune deletes things — enable it deliberately">
With `prune: true`, removing a file from Git removes the resource from the cluster. That's exactly what you want for true GitOps, but be sure your Git repo really is the complete source of truth before enabling it.
</Warning>

# Self-Healing in Action

Self-heal is what makes the cluster tamper-resistant. Suppose someone scales a deployment by hand:

<Terminal
  command="kubectl scale deployment guestbook --replicas=10"
  output={`deployment.apps/guestbook scaled`}
/>

Git still says 3 replicas. Argo CD detects the drift and, with `selfHeal: true`, reverts it:

<Terminal
  command="argocd app get guestbook"
  output={`Sync Status:  Synced to main (a1b2c3d)
Health:       Healthy
# replicas back to 3 — manual change reverted automatically`}
/>

The lesson: **change the cluster by changing Git**, never by hand.

# Sync Waves — Controlling Order

Some resources must exist before others (a database before the app that uses it, a namespace before its contents). **Sync waves** let you order the rollout using an annotation:

<CommandBlock command={`metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "0"    # runs first (lower = earlier)`} language="yaml" />

Resources in wave `0` sync and become healthy before wave `1` starts, and so on. Negative numbers run even earlier. This is how you sequence dependencies cleanly.

<Tip title="Hooks for one-off steps">
For things like database migrations, use resource **hooks** (`PreSync`, `Sync`, `PostSync`) — jobs that run at a specific point in the sync, e.g. run a migration `PreSync` before the new app version rolls out.
</Tip>

# How Argo CD Assesses Health

Sync status answers "does the cluster match Git?" — **health** answers "are the resources actually working?" Argo CD has built-in health checks per resource kind:

| Resource | Healthy when… |
|----------|---------------|
| Deployment | Desired replicas are available and updated |
| Service | Allocated correctly (LoadBalancer has an address) |
| Ingress | Load balancer is provisioned |
| Pod | Running / succeeded |

An app can be `Synced` but `Degraded` — e.g. the manifests applied fine, but the pods are crash-looping. Watching both statuses together tells the full story.

# 💼 Interview Preparation

<InterviewPrep question="What's the difference between sync status and health status in Argo CD?">
  They answer two different questions:

  - **Sync status** — *does the live cluster match what's in Git?* Values are `Synced` or `OutOfSync`. It's about configuration correctness.
  - **Health status** — *are the deployed resources actually functioning?* Values like `Healthy`, `Progressing`, `Degraded`. It's about runtime behaviour.

  You can be `Synced` but `Degraded` (correct config, crashing pods) or `OutOfSync` but `Healthy` (running fine, but Git has a newer change not yet applied). Good operators watch both — sync tells you if GitOps is up to date, health tells you if the app works.
</InterviewPrep>
