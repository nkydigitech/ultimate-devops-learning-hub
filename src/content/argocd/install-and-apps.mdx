# Step 1 — Install Argo CD

Argo CD installs as a set of pods in its own namespace:

<CommandBlock command={`kubectl create namespace argocd
kubectl apply -n argocd -f \\
  https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml`} />

<Terminal
  command="kubectl get pods -n argocd"
  output={`NAME                                  READY   STATUS    RESTARTS   AGE
argocd-server-6b7d9f7c8-xk2lm         1/1     Running   0          60s
argocd-repo-server-77c9c4b8d-9wq4t    1/1     Running   0          60s
argocd-application-controller-0       1/1     Running   0          60s
argocd-redis-5b6f8d799-2pnzt          1/1     Running   0          60s`}
/>

The **application-controller** is the reconciliation engine; the **repo-server** fetches and renders manifests from Git; the **server** hosts the API and UI.

---

# Step 2 — Log In

Get the auto-generated admin password and log in with the CLI:

<CommandBlock command={`# initial admin password
kubectl -n argocd get secret argocd-initial-admin-secret \\
  -o jsonpath="{.data.password}" | base64 -d

# port-forward the UI to your machine
kubectl port-forward svc/argocd-server -n argocd 8080:443

# log in with the CLI
argocd login localhost:8080`} />

<Warning title="Change the default password">
The initial admin password is stored in a secret for bootstrap only. Change it immediately (`argocd account update-password`) and, in real setups, wire Argo CD to your SSO instead of using the local admin account.
</Warning>

# Step 3 — Define an Application

An **Application** is just another Kubernetes resource. It says: *"take the manifests in this Git path and deploy them to this cluster/namespace."*

<CommandBlock command={`apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: guestbook
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/your-org/guestbook.git
    targetRevision: main
    path: k8s                 # folder in the repo holding the manifests
  destination:
    server: https://kubernetes.default.svc
    namespace: guestbook
  syncPolicy:
    syncOptions:
      - CreateNamespace=true`} language="yaml" />

Apply it like any manifest:

<CommandBlock command={`kubectl apply -f guestbook-app.yaml`} />

---

# Step 4 — Sync It

Right after creation the app is `OutOfSync` — defined in Git but not yet applied. Sync it to deploy:

<CommandBlock command={`# via CLI
argocd app sync guestbook

# check status
argocd app get guestbook`} />

<Terminal
  command="argocd app get guestbook"
  output={`Name:               guestbook
Project:            default
Sync Status:        Synced to main (a1b2c3d)
Health Status:      Healthy

GROUP  KIND        NAMESPACE  NAME        STATUS  HEALTH
       Service     guestbook  guestbook   Synced  Healthy
apps   Deployment  guestbook  guestbook   Synced  Healthy`}
/>

`Synced` + `Healthy` means the cluster now matches Git and the workloads are running. You just did your first GitOps deploy.

<Tip title="You can also create apps from the UI">
The web UI has a "New App" form that produces the same Application resource. Under the hood it's identical YAML — prefer committing that YAML to Git so even your apps are managed via GitOps.
</Tip>

# 💼 Interview Preparation

<InterviewPrep question="Walk through what happens when you create an Argo CD Application and sync it.">
  A clear end-to-end story:

  1. You commit manifests to Git and create an **Application** resource pointing at that repo/path.
  2. The **repo-server** clones the repo and renders the manifests (plain YAML, Helm, or Kustomize).
  3. The **application-controller** compares the rendered desired state against the live cluster — initially `OutOfSync`.
  4. On **sync** (manual or automated), Argo CD applies the manifests to the destination namespace.
  5. It reports **Sync status** (matches Git?) and **Health status** (resources healthy?), and keeps watching for drift.

  From then on, changing the app is just committing to Git — Argo CD reconciles the rest.
</InterviewPrep>
