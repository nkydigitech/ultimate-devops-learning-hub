# How SSH Works

SSH creates an **encrypted tunnel** between your machine and a remote server — no password is ever sent in plain text.

<CommandBlock command={`Your Laptop  (SSH client)
   ↓
 Internet    (encrypted, port 22)
   ↓
Remote Linux Server  (sshd)
   ↓
Your terminal session`} language="text" />

---

# SSH Key Pairs

SSH uses public/private key authentication:

- **Private key** — stays on your machine. **Never share it.**
- **Public key** — goes on the server. Safe to share.

When you connect, the server challenges your client to prove it holds the private key matching the public key on file.

---

# Generate an SSH Key

<CommandBlock command={'ssh-keygen -t ed25519 -C "your-email@example.com"'} />

Accept the default location and set a passphrase. This creates two files:

<CommandBlock command={`~/.ssh/id_ed25519        # private key — never share this
~/.ssh/id_ed25519.pub    # public key — copy this to servers`} language="text" />

<Terminal
  command="cat ~/.ssh/id_ed25519.pub"
  output="ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... your-email@example.com"
/>

---

# Connect to a Remote Server

<CommandBlock command={`ssh username@server-ip                       # basic connection
ssh ubuntu@54.123.45.67                      # e.g. Ubuntu on AWS EC2
ssh -i ~/.ssh/my-key.pem ubuntu@54.123.45.67 # using an AWS .pem key`} />

Copy your public key so you can log in without a password:

<CommandBlock command="ssh-copy-id ubuntu@54.123.45.67" />

---

# SSH Config — Stop Typing Long Commands

Instead of retyping addresses, define hosts in `~/.ssh/config`:

<CommandBlock command={`Host myserver
    HostName 54.123.45.67
    User ubuntu
    IdentityFile ~/.ssh/id_ed25519`} language="text" />

Now connect with just:

<CommandBlock command="ssh myserver" />

# Copy Files Securely with SCP

<CommandBlock command={`scp localfile.txt ubuntu@54.123.45.67:/home/ubuntu/   # upload
scp ubuntu@54.123.45.67:/var/log/app.log ./            # download
scp -r ./myfolder ubuntu@54.123.45.67:/home/ubuntu/    # whole folder`} />

# Troubleshooting

| Problem | Cause | Fix |
|---|---|---|
| `Permission denied (publickey)` | Wrong key or not copied | `ssh-copy-id` or check the `-i` path |
| `Connection refused` | `sshd` not running / wrong port | Confirm the SSH service is running |
| `Connection timed out` | Firewall blocking port 22 | Check the security group / firewall |
| `Unprotected private key file` | Key permissions too open | `chmod 400 ~/.ssh/id_ed25519` |

<Warning title="Protect your private key">
If SSH refuses to use your key with an "unprotected private key" warning, tighten the permissions: `chmod 600 ~/.ssh/id_ed25519`. A private key readable by others is a security hole.
</Warning>

# 💼 Interview Preparation

<InterviewPrep question="Why is SSH key authentication preferred over passwords?">
  Key-based authentication is both more secure and more convenient:

  - **Stronger:** A 256-bit key is far harder to brute-force than a typical password.
  - **No secret in transit:** The private key never leaves your machine — only a cryptographic proof is exchanged.
  - **Automation-friendly:** Scripts and CI/CD systems can authenticate without embedding a password.
  - **Revocable per key:** You can add or remove individual public keys on a server without changing a shared password.

  Best practice is to disable password login entirely on production servers and allow only key-based access.
</InterviewPrep>
