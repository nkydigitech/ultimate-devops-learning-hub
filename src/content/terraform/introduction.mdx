Clicking through a cloud console to create servers works once — but it's slow, error-prone, and impossible to reproduce. **Terraform** lets you describe your infrastructure in code, so you can create, change, and destroy it reliably and repeatably. This is **Infrastructure as Code (IaC)**.

# What is Infrastructure as Code?

Instead of manually provisioning servers, networks, and databases through a web console, you write **code** that describes what you want. That code is:

- **Version-controlled** — every change is tracked in Git.
- **Reviewable** — infrastructure changes go through pull requests.
- **Repeatable** — spin up an identical environment any time.
- **Documented** — the code *is* the documentation.

<Tip title="Click-ops vs code">
Manually clicking in a console is "click-ops": fast to start, impossible to reproduce. IaC trades a little upfront effort for infrastructure you can rebuild identically, forever.
</Tip>

---

# What Makes Terraform Special

Terraform is **cloud-agnostic** and **declarative**:

- **Cloud-agnostic** — the same tool manages AWS, Azure, GCP, Kubernetes, and hundreds of other platforms through *providers*.
- **Declarative** — you describe the desired end state, and Terraform figures out the steps to get there (create, update, or delete resources as needed).

<CommandBlock command={`You write:  "I want 3 servers and a load balancer"
Terraform:  compares desired vs actual → makes the minimal changes`} language="text" />

---

# The Building Blocks

| Concept | What it is |
|---------|------------|
| **Provider** | A plugin for a platform (aws, azurerm, google, kubernetes) |
| **Resource** | A single piece of infrastructure (a server, a bucket, a DNS record) |
| **State** | Terraform's record of what it has created |
| **Plan** | A preview of the changes Terraform will make |

A tiny example that creates an AWS S3 bucket:

<CommandBlock command={`terraform {
  required_providers {
    aws = { source = "hashicorp/aws" }
  }
}

provider "aws" {
  region = "us-east-1"
}

resource "aws_s3_bucket" "data" {
  bucket = "my-devops-course-bucket"
}`} language="hcl" />

The language is **HCL** (HashiCorp Configuration Language) — readable and purpose-built for infrastructure.

# The Core Workflow

Three commands do almost everything:

<CommandBlock command={`terraform init      # download providers, set up the working dir
terraform plan      # preview what will change
terraform apply     # make it real
terraform destroy   # tear it all down`} />

<Terminal
  command="terraform plan"
  output={`Terraform will perform the following actions:

  # aws_s3_bucket.data will be created
  + resource "aws_s3_bucket" "data" {
      + bucket = "my-devops-course-bucket"
      + id     = (known after apply)
    }

Plan: 1 to add, 0 to change, 0 to destroy.`}
/>

`plan` shows you *exactly* what will happen before anything changes — no surprises.

# 💼 Interview Preparation

<InterviewPrep question="Why is Infrastructure as Code important, and why Terraform specifically?">
  IaC brings software-engineering discipline to infrastructure:

  - **Reproducibility:** rebuild identical environments (dev, staging, prod) from the same code.
  - **Version control & review:** infrastructure changes are tracked in Git and reviewed like code.
  - **Auditability:** every change is recorded, which matters for compliance.
  - **Disaster recovery:** recreate everything from code if it's lost.

  Terraform stands out because it's **cloud-agnostic** (one tool, many providers), **declarative**, and has a huge provider ecosystem — so teams standardise on it across AWS, Azure, GCP, and beyond.
</InterviewPrep>
