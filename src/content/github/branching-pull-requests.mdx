# Working with Branches

<CommandBlock command={`git branch                     # list branches
git switch -c feature-login    # create + switch to a new branch
git switch main                # switch back to main`} />

<Terminal
  command="git switch -c feature-login"
  output="Switched to a new branch 'feature-login'"
/>

Think of `main` as the trusted, always-working version. You build on a branch, then merge it back when it's ready.

---

# Merging

Once your feature works, merge it into `main`:

<CommandBlock command={`git switch main
git merge feature-login`} />

If no one else changed the same lines, Git merges cleanly.

---

# Resolving a Merge Conflict

A **conflict** happens when two branches change the same lines. Git pauses and marks the file:

<CommandBlock command={`<<<<<<< HEAD
Welcome to our app!
=======
Welcome to the DevOps Hub!
>>>>>>> feature-login`} language="text" />

Edit the file to keep what you want, remove the `<<<`, `===`, `>>>` markers, then:

<CommandBlock command={`git add index.html
git commit -m "Resolve merge conflict in index.html"`} />

<Warning title="Conflicts are normal">
A merge conflict is not an error or a bug — it just means Git needs a human to decide which change wins. Read both sides carefully before resolving.
</Warning>

# The Pull Request Workflow

On a team you rarely merge straight into `main`. Instead:

<CommandBlock command={`git switch -c feature-login
# ... make changes, commit ...
git push -u origin feature-login`} language="text" />

Then on GitHub you open a **Pull Request (PR)** — a request to merge your branch into `main`. A PR lets teammates **review the code, comment, and approve** before it's merged, and it's what usually triggers your CI/CD pipeline.

<Tip title="You already saw a PR">
The fix for this very learning hub was delivered as a pull request rather than a direct push — exactly so the changes could be reviewed before going live. That's the workflow in action.
</Tip>

# 💼 Interview Preparation

<InterviewPrep question="What's the difference between git merge and git rebase?">
  Both integrate changes from one branch into another, but differently:

  - **Merge** creates a new "merge commit" that ties the two histories together. History is preserved exactly as it happened — non-destructive but can look tangled.
  - **Rebase** replays your branch's commits on top of the target branch, producing a linear history as if you'd branched from the latest `main`. Cleaner, but it rewrites commit hashes.

  Common rule of thumb: **rebase** your local feature branch to keep it tidy before merging, but **never rebase** commits that others have already pulled, because rewriting shared history breaks their copies.
</InterviewPrep>
