Running other people's images is useful, but the real power is packaging **your own** app. A **Dockerfile** is a plain-text recipe that tells Docker how to build your image, step by step.

- Apply best practices for small, cached, secure images

# The Core Instructions

| Instruction | What it does |
|-------------|--------------|
| `FROM` | The base image to build on |
| `WORKDIR` | Set the working directory inside the image |
| `COPY` | Copy files from your project into the image |
| `RUN` | Execute a command at build time (install deps) |
| `EXPOSE` | Document which port the app listens on |
| `CMD` | The command that runs when the container starts |

# A Real Dockerfile

Here's a complete Dockerfile for a small Node.js app:

<CommandBlock command={`# 1. Start from an official, slim base image
FROM node:20-slim

# 2. Set the working directory
WORKDIR /app

# 3. Copy dependency manifests first (better caching)
COPY package*.json ./

# 4. Install dependencies
RUN npm install --production

# 5. Copy the rest of the source code
COPY . .

# 6. Document the port the app uses
EXPOSE 3000

# 7. Command to start the app
CMD ["node", "server.js"]`} language="dockerfile" />

<Tip title="Why copy package.json first?">
Docker caches each instruction as a layer. By copying `package.json` and installing deps *before* copying your code, Docker only re-runs `npm install` when your dependencies change — not on every code edit. This makes rebuilds dramatically faster.
</Tip>

# Build and Run Your Image

<CommandBlock command={`docker build -t myapp:1.0 .        # build, tag it myapp:1.0
docker run -d -p 3000:3000 myapp:1.0`} />

<Terminal

The `-t` flag **tags** the image with a name and version, so you can run and share it easily.

# Best Practices

<Warning title="Don't run as root">
By default containers run as root, which is risky. Add a non-root user and switch to it with `USER appuser` before your `CMD`. It's a small change that greatly reduces the blast radius of a compromise.
</Warning>

A few habits that separate good images from bad:

- **Use slim/alpine base images** — smaller images pull faster and have fewer vulnerabilities.
- **Add a `.dockerignore`** — keep `node_modules`, `.git`, and secrets out of the build context.
- **Order layers by change frequency** — least-changing instructions first for maximum cache reuse.
- **One process per container** — a container should do one job well.
- **Use multi-stage builds** — compile in a big image, then copy only the artifact into a tiny final image.

<CommandBlock command={`# Multi-stage build: build stage + tiny runtime stage
FROM node:20 AS build
WORKDIR /app
COPY . .
RUN npm ci && npm run build

FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html`} language="dockerfile" />

# 💼 Interview Preparation

<InterviewPrep question="How would you reduce the size of a Docker image?">
  Several proven techniques:

  - **Choose a minimal base** — `alpine` or `-slim` variants instead of full OS images.
  - **Multi-stage builds** — leave build tools behind, ship only the artifact.
  - **Combine and clean up `RUN` steps** — remove package caches in the same layer they're created.
  - **Use `.dockerignore`** — avoid copying unnecessary files into the build context.
  - **Install only production dependencies** — skip dev/test packages in the final image.

  Smaller images pull faster, deploy quicker, and expose a smaller attack surface.
</InterviewPrep>
