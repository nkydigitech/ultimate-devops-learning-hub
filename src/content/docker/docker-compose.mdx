Real applications aren't one container — they're an app **plus** a database, maybe a cache, maybe a queue. Starting each by hand with long `docker run` commands is error-prone. **Docker Compose** lets you describe the whole stack in one YAML file and start it all with a single command.

# Why Compose?

Without Compose, launching an app + database means several long commands, a shared network, and correct startup order — every single time. Compose captures all of that in a file you can version-control and share.

<Tip title="The one-line version">
Compose is a recipe for your *whole application*: every service, its config, and how they connect — reproducible with one command.
</Tip>

# A Compose File, Explained

Here's a typical stack: a web app talking to a PostgreSQL database.

<CommandBlock command={`services:
  web:
    build: .                 # build from the local Dockerfile
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://user:pass@db:5432/app
    depends_on:
      - db

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:`} language="yaml" />

Key ideas:

- Each entry under `services` is a container.
- `depends_on` controls startup order.
- The web app reaches the database using the **service name** `db` as the hostname — Compose creates a private network where services find each other by name.
- The named volume `pgdata` keeps database data safe across restarts.

<Warning title="Never commit real secrets">
The passwords above are fine for a local demo, but never put real credentials in a committed Compose file. Use a `.env` file (git-ignored) or a secrets manager for anything real.
</Warning>

# Running the Stack

| Command | What it does |
|---------|--------------|
| `docker compose up -d` | Build and start all services (detached) |
| `docker compose ps` | List the stack's containers |
| `docker compose logs -f` | Follow logs from all services |
| `docker compose down` | Stop and remove everything |
| `docker compose down -v` | ...and delete the volumes too |

<Terminal
  command="docker compose up -d"
  output={`[+] Running 3/3
 ✔ Network app_default    Created
 ✔ Container app-db-1      Started
 ✔ Container app-web-1     Started`}
/>

One command brought up a private network, the database, and the web app in the right order.

# Service Discovery by Name

This is the part that trips up beginners: inside a Compose network, you connect to another service by its **service name**, not `localhost`.

<CommandBlock command={`# Correct — 'db' is the service name
DATABASE_URL=postgres://user:pass@db:5432/app

# Wrong — localhost points at the app's own container
DATABASE_URL=postgres://user:pass@localhost:5432/app`} language="bash" />

<Tip title="Remember">
Each container has its own `localhost`. To reach another container, use its **service name** as the hostname.
</Tip>

# 💼 Interview Preparation

<InterviewPrep question="When would you use Docker Compose, and when would you reach for Kubernetes instead?">
  They serve different scales:

  - **Docker Compose** is ideal for **local development** and simple single-host deployments. It's simple, fast, and reproducible — perfect for spinning up your full stack on a laptop or a CI runner.
  - **Kubernetes** is for **production at scale**: multiple hosts, automatic scaling, self-healing, rolling updates, and service discovery across a cluster.

  A common path is: develop with Compose, then deploy to Kubernetes. Understanding Compose first makes Kubernetes concepts much easier to grasp — which is exactly where we go next.
</InterviewPrep>
