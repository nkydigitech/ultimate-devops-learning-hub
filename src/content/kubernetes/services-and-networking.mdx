Pods are disposable and their IP addresses change every time they're recreated. So how does the rest of your system reliably reach them? The answer is a **Service** — a stable network endpoint that always points to a healthy set of Pods.

# Why Services Exist

Each Pod gets its own IP, but that IP disappears when the Pod is replaced. If your frontend hard-coded a backend Pod's IP, it would break constantly.

A **Service** solves this: it has a stable IP and DNS name, and automatically load-balances across whatever healthy Pods currently match its label selector.

<CommandBlock command={`Frontend ──▶ Service (stable) ──┬──▶ Pod (changes)
              backend:80        ├──▶ Pod (changes)
                                └──▶ Pod (changes)`} language="text" />

---

# How a Service Finds Pods

Services use **labels**, not IPs. The Service's `selector` matches the labels on the Pods:

<CommandBlock command={`apiVersion: v1
kind: Service
metadata:
  name: backend
spec:
  selector:
    app: web          # match Pods labelled app=web
  ports:
    - port: 80        # the Service port
      targetPort: 80  # the Pod's container port`} language="yaml" />

Any Pod with the label `app: web` is automatically added to this Service — no matter when it was created or what its IP is.

<Tip title="Service discovery by DNS">
Inside the cluster, other Pods reach this Service simply as `backend` (or `backend.namespace.svc.cluster.local`). Kubernetes runs an internal DNS that resolves Service names automatically.
</Tip>

# The Service Types

| Type | Reachable from | Use for |
|------|----------------|---------|
| **ClusterIP** (default) | Inside the cluster only | Internal communication between services |
| **NodePort** | A port on every node's IP | Simple external access / testing |
| **LoadBalancer** | A cloud load balancer with a public IP | Production external access on cloud |

<CommandBlock command={`# Expose the deployment as different service types
kubectl expose deployment web --port=80 --type=ClusterIP
kubectl expose deployment web --port=80 --type=NodePort
kubectl expose deployment web --port=80 --type=LoadBalancer`} />

<Terminal
  command="kubectl get svc"
  output={`NAME      TYPE           CLUSTER-IP     EXTERNAL-IP     PORT(S)
backend   ClusterIP      10.96.0.12     <none>          80/TCP
web       LoadBalancer   10.96.0.44     203.0.113.25    80:31840/TCP`}
/>

# Ingress — Smart HTTP Routing

Giving every service its own cloud LoadBalancer is expensive. An **Ingress** is a single entry point that routes HTTP traffic to many services based on hostname or path:

<CommandBlock command={`apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
spec:
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: backend
                port:
                  number: 80
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port:
                  number: 80`} language="yaml" />

<Tip title="Ingress needs a controller">
An Ingress object is just rules. You also need an **Ingress controller** (like NGINX Ingress or Traefik) running in the cluster to actually enforce them. It handles TLS termination and routing for all your services at once.
</Tip>

# 💼 Interview Preparation

<InterviewPrep question="Explain how traffic flows from a user's browser to a Pod in Kubernetes.">
  A complete path ties Services, Ingress, and Pods together:

  1. DNS resolves `shop.example.com` to the cluster's external load balancer / Ingress IP.
  2. The **Ingress controller** receives the request and matches it against Ingress rules (host + path).
  3. It forwards the request to the appropriate **Service** (ClusterIP).
  4. The Service load-balances the request to one of the healthy **Pods** matching its selector.
  5. The Pod's container handles the request and responds back along the same path.

  The key insight: Pods change constantly, but Services and Ingress provide the stable addresses that make this reliable.
</InterviewPrep>
