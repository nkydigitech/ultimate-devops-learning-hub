Your app needs configuration (URLs, feature flags) and secrets (passwords, API keys) — and it should never bake these into the image. It also needs to stay healthy and scale with demand. This lesson covers the production essentials that make a Deployment truly robust.

By the end of this lesson you will:

- Inject them into Pods as environment variables or files

# ConfigMaps — Configuration Outside the Image

A **ConfigMap** holds non-sensitive configuration as key-value pairs:

<CommandBlock command={`apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: "info"
  FEATURE_NEW_UI: "true"`} language="yaml" />

Inject it into a Pod as environment variables:

<CommandBlock command={`spec:
  containers:
    - name: app
      image: myapp:1.0
      envFrom:
        - configMapRef:
            name: app-config`} language="yaml" />

<Tip title="Why separate config from code?">
The same image should run in dev, staging, and production — only the config changes. Keeping config out of the image means one build promotes cleanly through every environment.
</Tip>

---

# Secrets — Sensitive Values

A **Secret** works like a ConfigMap but is meant for sensitive data (passwords, tokens, keys):

<CommandBlock command={`kubectl create secret generic db-secret \\
  --from-literal=DB_PASSWORD='s3cr3t'`} />

<Warning title="Secrets are base64, not encrypted by default">
Kubernetes Secrets are only base64-encoded in etcd, not truly encrypted out of the box. For real security, enable **encryption at rest** for etcd and restrict access with RBAC, or use an external secrets manager (Vault, cloud KMS).
</Warning>

Inject a Secret the same way you inject config:

<CommandBlock command={`env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: db-secret
        key: DB_PASSWORD`} language="yaml" />

# Health Probes

Kubernetes needs to know if your app is alive and ready. Two probes tell it:

| Probe | Question it answers | On failure |
|-------|---------------------|------------|
| **livenessProbe** | Is the app still alive? | Restart the container |
| **readinessProbe** | Is the app ready for traffic? | Remove it from the Service until ready |

<CommandBlock command={`livenessProbe:
  httpGet:
    path: /healthz
    port: 3000
  initialDelaySeconds: 10
  periodSeconds: 10
readinessProbe:
  httpGet:
    path: /ready
    port: 3000
  periodSeconds: 5`} language="yaml" />

<Tip title="Readiness enables zero-downtime deploys">
During a rolling update, traffic is only sent to Pods that pass their readiness probe. A new Pod that's still starting up won't receive requests until it's genuinely ready.
</Tip>

# Autoscaling with the HPA

The **Horizontal Pod Autoscaler** adds or removes Pods automatically based on metrics like CPU usage:

<CommandBlock command={`kubectl autoscale deployment web \\
  --cpu-percent=70 --min=2 --max=10`} />

<Terminal
  command="kubectl get hpa"
  output={`NAME   REFERENCE        TARGETS   MINPODS   MAXPODS   REPLICAS
web    Deployment/web   45%/70%   2         10        3`}
/>

When average CPU crosses 70%, the HPA scales up toward 10 Pods; when load drops, it scales back down toward 2. This requires resource **requests** to be set on the containers so the HPA has a baseline to measure against.

# 💼 Interview Preparation

<InterviewPrep question="How would you make a Kubernetes app production-ready?">
  Layer on the essentials beyond just a running Deployment:

  - **Config & secrets** externalised into ConfigMaps and Secrets (secrets encrypted at rest).
  - **Resource requests and limits** so the scheduler places Pods well and the HPA can scale.
  - **Liveness and readiness probes** for self-healing and zero-downtime rollouts.
  - **Horizontal Pod Autoscaler** to handle variable load automatically.
  - **Multiple replicas across nodes** for high availability.
  - **RBAC and network policies** to lock down access.

  These turn "it runs" into "it runs reliably under real production conditions."
</InterviewPrep>
