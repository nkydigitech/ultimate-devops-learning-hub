# The Data Model

Every sample Prometheus stores is a **time series** identified by a metric name plus a set of labels:

<CommandBlock command={`http_requests_total{method="GET", path="/api", status="200"}
└──────┬──────┘ └──────────────────┬───────────────────┘
   metric name                   labels`} language="text" />

Each unique combination of name + labels is its own series, sampled over time. Labels are what make metrics powerful — you can later filter and aggregate across any dimension.

<Warning title="Watch your label cardinality">
Never put unbounded values (like a user ID, email, or request ID) in a label. Each unique value creates a new time series, and millions of series will overwhelm Prometheus. Keep labels to small, finite sets like `status`, `method`, or `region`.
</Warning>

---

# The Four Metric Types

| Type | Meaning | Example |
|------|---------|---------|
| **Counter** | Only goes up (reset on restart) | Total requests served |
| **Gauge** | Goes up and down | Current memory in use, temperature |
| **Histogram** | Buckets of observations | Request duration distribution |
| **Summary** | Similar to histogram, client-side quantiles | Request latency percentiles |

The rule of thumb: use a **counter** for things you accumulate, a **gauge** for things that fluctuate, and a **histogram** for distributions like latency.

# Configuring a Scrape

Prometheus reads a YAML config that lists what to scrape and how often:

<CommandBlock command={`global:
  scrape_interval: 15s          # how often to scrape every target

scrape_configs:
  - job_name: "prometheus"      # Prometheus scraping itself
    static_configs:
      - targets: ["localhost:9090"]

  - job_name: "my-app"
    static_configs:
      - targets: ["app:8080"]   # scrapes http://app:8080/metrics`} language="yaml" />

Start Prometheus pointing at that file and it begins scraping immediately:

<Terminal
  command="prometheus --config.file=prometheus.yml"
  output={`level=info msg="Starting Prometheus"
level=info msg="Server is ready to receive web and API requests."
level=info msg="Scrape pool started" job=my-app`}
/>

<Tip title="Exporters do the work for you">
Can't add metrics to something you don't control (like a Linux host or PostgreSQL)? Run an **exporter** — a small sidecar that translates system stats into a `/metrics` endpoint. `node_exporter` (hosts) and `blackbox_exporter` (probing URLs) are the most common.
</Tip>

# Querying with PromQL

Open the Prometheus UI at port 9090 and type queries. The simplest query is just a metric name — but the real power is filtering and functions.

**Filter by label:**

<CommandBlock command={`http_requests_total{status="500"}`} language="text" />

**Rate of increase — the single most useful function.** Counters always climb, so you rarely graph them raw; instead you graph how fast they climb with `rate()`:

<CommandBlock command={`rate(http_requests_total{status="500"}[5m])`} language="text" />

This reads: *the per-second rate of 500 errors, averaged over the last 5 minutes.*

**Aggregate across series** with `sum`, `avg`, `by`:

<CommandBlock command={`sum(rate(http_requests_total[5m])) by (status)`} language="text" />

That gives you total request rate broken down by status code — exactly what you'd graph on a dashboard.

# 💼 Interview Preparation

<InterviewPrep question="What is label cardinality and why does it matter?">
  Cardinality is the number of unique time series a metric produces, driven by the number of unique label-value combinations. It matters because:

  - Prometheus keeps active series in memory; high cardinality causes huge memory use and slow queries.
  - A single careless label (like `user_id` or `request_id`) can explode one metric into millions of series.

  The fix is discipline: only use labels with small, bounded sets of values (status codes, methods, regions, service names). High-cardinality data belongs in logs or traces, not metric labels.
</InterviewPrep>
