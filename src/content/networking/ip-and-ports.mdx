To deliver a message, the network needs two things: **which machine** (the IP address) and **which program on that machine** (the port). Get these two ideas and a huge amount of networking suddenly makes sense.

# IP Addresses — the Machine's Location

An **IP address** is the address of a device on a network, like a street address for a house.

The most common form, IPv4, looks like `192.168.1.10` — four numbers (0–255) separated by dots.

## Private vs Public

| Type | Reachable from | Example ranges |
|------|----------------|----------------|
| **Private** | Only inside your local network | `10.x.x.x`, `172.16–31.x.x`, `192.168.x.x` |
| **Public** | Anywhere on the internet | Anything not in the private ranges |

<Tip title="Why this matters in the cloud">
Inside a cloud VPC, servers usually talk to each other over **private** IPs. Only a load balancer or gateway gets a **public** IP. This is the foundation of a secure network design.
</Tip>

---

# Ports — the Program's Door

One machine runs many programs at once — a web server, a database, an SSH service. A **port** (a number from 0–65535) tells the network *which program* should receive the message.

An address plus a port is called a **socket**: `192.168.1.10:443`.

## Common ports to memorise

| Port | Service |
|------|---------|
| 22 | SSH |
| 80 | HTTP |
| 443 | HTTPS |
| 53 | DNS |
| 3306 | MySQL |
| 5432 | PostgreSQL |
| 6379 | Redis |

<Warning title="Firewalls block ports">
If your app "won't connect," a closed port in a firewall or cloud security group is one of the most common causes. Always check: is the port open, and is the service actually listening on it?
</Warning>

---

# TCP vs UDP

Both live at the Transport layer, but they make different promises:

| | **TCP** | **UDP** |
|---|---------|---------|
| Reliable? | Yes — confirms delivery, resends lost data | No — fire and forget |
| Ordered? | Yes | No |
| Speed | Slightly slower (more checks) | Faster, lighter |
| Used for | Web, SSH, databases | DNS, video calls, gaming, metrics |

<Tip title="Rule of thumb">
Use **TCP** when every byte must arrive correctly (a web page, a bank transaction). Use **UDP** when speed matters more than perfection (a live video frame that's already out of date if it's late).
</Tip>

# See It Yourself

Check which ports are listening on your machine:

<CommandBlock command={`ss -tulnp        # show listening TCP/UDP ports (Linux)
curl -v http://localhost:80   # connect to a program on port 80`} />

<Terminal
  command="ss -tuln | grep LISTEN"
  output={`tcp   LISTEN  0  128  0.0.0.0:22    0.0.0.0:*
tcp   LISTEN  0  128  0.0.0.0:80    0.0.0.0:*
tcp   LISTEN  0  128  127.0.0.1:5432  0.0.0.0:*`}
/>

Here SSH (22) and a web server (80) accept connections from anywhere, while PostgreSQL (5432) only listens on `127.0.0.1` — localhost only. That's a deliberate security choice.

# 💼 Interview Preparation

<InterviewPrep question="A user reports they can't reach your service. How do you approach it?">
  Work up the layers, checking connectivity step by step:

  1. **DNS** — does the hostname resolve to the right IP? (`dig`, `nslookup`)
  2. **Reachability** — can you reach the machine at all? (`ping`)
  3. **Port** — is the service's port open and listening? (`ss`, `telnet`, `nc`)
  4. **Firewall / security group** — is traffic to that port allowed?
  5. **Application** — is the process actually running and healthy?

  This layered, methodical approach beats guessing and is exactly what interviewers want to hear.
</InterviewPrep>
